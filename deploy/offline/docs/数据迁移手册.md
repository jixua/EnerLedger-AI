# 当前 Dev 数据迁移手册

## 1. 数据边界

迁移包按数据真值源划分：

- MySQL：数据集、目录、文档元数据、分块、模型配置、队列/Outbox、报告任务和 Alembic 版本。
- MinIO：上传的原始文档、解析后的私有文件和预览资源。
- Qdrant：Dense 与 Sparse 向量索引。
- Manticore：BM25 索引。
- RabbitMQ：不迁移瞬时队列消息。目标环境由服务重新声明交换机、队列和绑定；MySQL Outbox/任务状态负责重投未完成业务任务。

`llm_config.api_key` 在 MySQL 中是密文，它依赖 `API_KEY_ENCRYPTION_SECRET`。只复制数据库而不复制对应加密密钥，会造成模型配置存在但不可用。

## 2. 一致性导出

导出脚本会产生一个短暂停机窗口：先停止前端、API、Parse Worker、Report Worker 和 Pi Agent，避免新增写入；MySQL 使用 `--single-transaction` 逻辑备份；随后停止 MinIO、Qdrant、Manticore并归档数据卷。脚本成功或异常退出都会尝试恢复被停止的源服务。

执行前准备一个权限为 `600`、不放入仓库的随机口令文件：

```bash
openssl rand -base64 48 > /安全路径/package-passphrase.txt
chmod 600 /安全路径/package-passphrase.txt
```

在 Dev Compose 根目录对应服务器上执行：

```bash
export SOURCE_COMPOSE_FILE=/实际路径/docker-compose.yml
export SOURCE_ENV_FILE=/实际路径/.env
export SOURCE_PROJECT_NAME=enerledger-dev
export PACKAGE_PASSPHRASE_FILE=/安全路径/package-passphrase.txt
export PACKAGE_API_IMAGE=enerledger-ai:package-<候选SHA>
export PACKAGE_FRONTEND_IMAGE=enerledger-web:package-<候选SHA>
export PACKAGE_PI_IMAGE=enerledger-pi:package-<候选SHA>
export OUTPUT_ROOT=/安全且空间充足的目录
deploy/offline/scripts/export-dev-package.sh
```

三个 `PACKAGE_*_IMAGE` 必须是已经在源服务器完成构建和静态验证、但没有替换当前 Dev 容器的候选镜像。部署包会把它们统一重标记为 `enerledger/api:offline`、`enerledger/frontend:offline` 和 `enerledger/pi-agent:offline`。

导出脚本会创建新的 `reviewer` 审核员账号：随机初始密码单独写入 `initial-reviewer-password.txt.enc`，密码哈希写入 `secrets.env.enc`。解密后应通过受控渠道交付账号，并在首次登录后轮换密码。

口令文件必须通过与部署包不同的安全渠道交付，不得放进压缩包、Git、工单正文或聊天日志。

## 3. 迁移前证据

`MANIFEST.txt` 至少记录：导出时间、Compose 项目、API/前端/Pi 源镜像、镜像 ID、源 Git revision 标签和 Alembic revision。`SHA256SUMS` 覆盖包内每个文件。

正式切换前还应记录以下源端数据量：

```sql
SELECT table_name, table_rows
FROM information_schema.tables
WHERE table_schema = DATABASE()
ORDER BY table_name;
```

同时记录 MinIO 桶对象数量与总大小、Qdrant collection 点数量、Manticore 索引文档数量。目标端必须用同一口径比对。

## 4. 恢复顺序

只能恢复到空项目名和空数据卷：

```bash
scripts/decrypt-secrets.sh /安全路径/package-passphrase.txt
scripts/restore-data.sh --confirm-empty-target
scripts/verify.sh
```

不要在导入备份前启动 API。API 入口会自动执行 `alembic upgrade heads`；若空库先被新镜像迁移，再导入旧结构，可能产生冲突。部署包使用与数据快照相同的 API 镜像，导入完成后启动时 Alembic 应保持无变更。

## 5. 版本升级

先恢复并验收与快照匹配的镜像，再升级业务镜像。升级步骤为：

1. 再次备份当前目标 MySQL 和四类持久化数据。
2. 记录 `alembic current` 和新镜像的 `alembic heads`。
3. 停止写入和 Worker。
4. 更新镜像并仅启动 API，让入口执行 `alembic upgrade heads`。
5. 核对 schema、业务行数、MinIO 对象、Qdrant/Manticore 查询。
6. 最后启动 Worker 和前端。

不得使用 `alembic stamp` 把旧库伪装成新版本。若源库来自旧 39 版迁移链，需要单独 ETL 和索引重建，不适用本包的一键恢复。

## 6. 故障处理

- MySQL 导入失败：保留日志，不在半成品库上反复执行；更换新的 `COMPOSE_PROJECT_NAME` 重做。
- 模型 Key 解密失败：核对源 `API_KEY_ENCRYPTION_SECRET`，不要盲目复制其他环境的密文。
- Qdrant 或 Manticore 版本不一致：使用包内固定镜像恢复，不先升级中间件。
- 检索结果缺失：分别检查 MySQL 文档状态、MinIO 原件、Qdrant 点数和 Manticore索引，不用单一健康接口替代数据验收。
- Worker 恢复后出现重复任务：先停止 Worker，核对 MySQL Outbox、租约和文档版本；不要清空 RabbitMQ 或业务表来掩盖问题。
