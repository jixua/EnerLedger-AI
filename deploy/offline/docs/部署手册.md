# Docker 离线部署手册

## 1. 适用范围

本手册用于把导出时的 EnerLedger-AI Dev 服务和数据完整迁移到一台新的 Linux Docker 主机。镜像和数据与 `MANIFEST.txt` 中记录的 Dev 版本绑定，不应混用其他 API 镜像或迁移 revision。

本次候选 API 镜像允许在“候选版本与源 Dev 的 `pyproject.toml`、`uv.lock` 完全相同”时使用 `Dockerfile.api-layered`，在已验证 Dev 基础镜像上替换完整 `/app/app`、`/app/migrations` 和 `/app/reporting`。`docker image save` 会把所有基础层一并写入离线归档，目标服务器不依赖源 Dev 镜像。若两个依赖文件有任何差异，必须执行完整 Dockerfile 构建，不能使用分层快捷方式。

建议普通业务至少使用 8 核 CPU、16 GB 内存、80 GB 可用 SSD；包含大型扫描 PDF 或批量解析时建议 8 核、32 GB，或单独部署解析节点。4 核、8 GB 只适合低并发且必须保持文档解析并发为 1。

目标主机需要：

- x86_64 Linux；若目标是 ARM64，必须重新构建业务镜像，不能直接加载 x86_64 归档。
- Docker Engine 24 或更高版本、Docker Compose v2。
- 足够容纳“解压后的镜像 + 数据卷 + 至少 30% 运行余量”的磁盘空间。
- `gzip`、`sha256sum`、`openssl`、`curl`。
- 目标端口默认：前端 8080、API 8000、MinIO 9000/9001。数据库、Qdrant、Manticore、RabbitMQ 默认不暴露到宿主机。

## 2. 部署前检查

```bash
docker version
docker compose version
df -h
sha256sum -c SHA256SUMS
cat MANIFEST.txt
```

部署包包含业务数据和加密配置，应限制目录权限：

```bash
chmod 700 .
chmod 600 secrets.env.enc
```

通过独立安全渠道取得导出时的口令文件，然后解密环境配置：

```bash
scripts/decrypt-secrets.sh /安全路径/package-passphrase.txt
```

打开 `.env` 核对 `MINIO_PUBLIC_ENDPOINT`、宿主机端口、CORS 域名和外部模型地址。迁移 `llm_config` 时必须保持源环境的 `API_KEY_ENCRYPTION_SECRET`，否则已有模型 API Key 无法解密。数据库密码包含 `@`、`:`、`/` 等 URL 保留字符时，应在 `DATABASE_URL` 中使用 URL 编码后的值。

## 3. 首次恢复

恢复命令只允许在全新目标上执行。它会拒绝任何已存在的同名数据卷：

```bash
scripts/restore-data.sh --confirm-empty-target
```

脚本依次完成：

1. 从本地归档导入所有 Docker 镜像。
2. 创建独立命名卷。
3. 恢复 MinIO、Qdrant、Manticore 数据卷。
4. 启动基础服务并等待 MySQL 健康。
5. 导入完整 MySQL schema、数据和 Alembic revision。
6. 启动 Pi Agent、API、Parse Worker 和前端。

报告生成默认不启动。需要启用时先设置报告模型和 Token，再执行：

```bash
ENABLE_REPORTS=true scripts/restore-data.sh --confirm-empty-target
```

## 4. 验收

```bash
scripts/verify.sh
docker compose --env-file .env -f docker-compose.yml ps
docker compose --env-file .env -f docker-compose.yml logs --tail=200 api
docker compose --env-file .env -f docker-compose.yml logs --tail=200 parse-worker
```

必须分别确认：

- 所有必需容器为 `running`，带健康检查的容器为 `healthy`。
- `/health/live` 返回 `{"status":"ok"}`。
- `alembic current` 与 `MANIFEST.txt` 完全一致。
- 登录后 `/api/v1/auth/me` 显示审核员角色，审核员只能访问对话和资料审核，不能进入数据集、模型、任务或系统管理接口。
- MySQL 业务表行数与源环境导出记录一致。
- MinIO 两个业务桶存在，抽查原文件可下载。
- Qdrant collection、点数量与源环境一致。
- Manticore 的数据集索引存在，抽查检索可返回内容。
- 使用真实管理员账号登录，完成数据集浏览、文档预览和一次带引用的对话。

HTTP 200 健康检查只证明进程存活，不等于数据迁移和检索验收完成。

## 5. 运维命令

```bash
docker compose --env-file .env -f docker-compose.yml ps
docker compose --env-file .env -f docker-compose.yml logs -f api parse-worker
docker compose --env-file .env -f docker-compose.yml restart api parse-worker
docker compose --env-file .env -f docker-compose.yml stop
docker compose --env-file .env -f docker-compose.yml start
```

不得对仍需保留数据的环境执行 `docker compose down -v`。

## 6. 回滚

首次切换前保留旧 Dev 环境，不修改源数据。若新环境验收失败：

1. 停止新环境对外流量和写入。
2. 重新指向旧环境。
3. 保留新环境容器日志和数据卷用于分析，不立即删除。
4. 若新环境已经产生业务写入，先单独导出增量数据，再决定回滚或重新迁移。

部署包恢复本身不会修改源 Dev；源服务只在一致性导出窗口内短暂停止，并由导出脚本恢复。
